## How this session started

Not with the errors. The session opened with a reported `test-quality` failure in the
quality gate, and the first real finding was that there was nothing to fix: eleven
`ambient-calendar-in-test` errors across `DOSTimeTests` and `ZIPWriterTests` were a
false positive in the gate, not a defect here. Every flagged site already pinned its
zone as a sibling argument:

```swift
DateComponents(calendar: Calendar(identifier: .gregorian),
               timeZone: TimeZone(identifier: "UTC"), ...)
```

`DateComponents.timeZone` overrides the calendar's, verified by resolving the same
components under three time zones and getting one instant. `quality-gate-swift` commit
`3ceb94a` had already added the carve-out; the runs that failed used a binary two days
stale. The gate's own source names these eleven sites as its finding population,
"every one of them exemplary code."

A `TestCalendar` fixture was built to deduplicate the eleven blocks before that was
known, and was reverted once it was. Correct code should not be churned to route around
a bug that no longer exists.

**What shipped from that:** `e22aa2d`, ratcheting `minimumGateVersion` to 2026-09-19 so
a pre-carve-out binary refuses to run rather than reporting phantom errors.

## What 0.7.0 actually is

Three containers had arrived with three error enums, and they no longer agreed:

| `ZIPError` | `GzipMember.Failure` | `ZlibStream.Failure` |
|---|---|---|
| `truncatedArchive` | `tooShort` | `tooShort`, `truncated` |
| `invalidSignature` | `notGzip` | `notZlib` |
| `checksumMismatch(path:…)` | `checksumMismatch(…)` | — |

Two nested types both named `Failure`. `checksumMismatch` carrying a path in one and
not the other, so no single branch could handle both. Fifteen cases; seven now.

Which container failed is not carried in the error, because the call site already says
it — `.invalidSignature` out of `GzipMember.decompress` means "not gzip".

Done at 0.x deliberately. 1.0 freezes the vocabulary, and unifying afterwards costs a
major version.

## Process

Followed Design → RED → GREEN → REFACTOR → DOCUMENT → VERIFY:

- `plans/proposals/0002-UnifiedErrors.md` written first, with the full case mapping
- Tests rewritten to the new vocabulary **before** the type existed; build failure
  confirmed (`type 'ZIPError' has no member 'truncated'`)
- Implementation, then docs, then gate
- `ZlibStreamTests` had four `#expect(throws: (any Error).self)` assertions — tightened
  to named cases while the vocabulary was being touched anyway

## Doc reconciliation

The master plan had drifted further than the code:

- Core Architectural Decision #4 still said the writer does not compress. It has since
  Phase 4.
- Decision #5 still said "No ZIP64 … sufficient for document formats." That premise
  failed within three months when SwiftXLSX needed more than 65,535 entries.
- The Public API block had never been updated past 0.1 — no `CompressionLevel`, no
  `ZlibStream`, no `GzipMember`, and four of `ZIPEntry`'s six initialiser parameters
  missing.

Both decisions struck through with their reasoning kept rather than deleted. README
also advertised a ZIP64 threshold of 65,534 entries; the format's limit is 65,535.

## 1.0 is now defined

Phase 7 *is* 1.0: streaming reader, progress callback, Linux, multi-member gzip,
password archives. The public surface is already stable enough to freeze — nothing
outstanding requires a breaking change, which is exactly why 0.7.0 spent its breaking
change now. What 1.0 adds is that the documented limitations are gone rather than
merely documented.

Multi-member gzip is the one item that changes existing behaviour, so it lands before
1.0 or not at all.
